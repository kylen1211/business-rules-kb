# 步 1 · 概览

判断类，单独做，人审后才进下一步。骨架档、细节档都走。

## 范围

看全貌——graphify 圈出这个业务经过的文件；定业务前缀；列出有哪几条链路；写管什么 / 不管什么。**文件清单只记录链路实际触碰到的全部文件，不做归属判断**（文件本身被多业务共用是正常现象，不等于规则冲突；归属判断粒度下放到步 2 / 步 3 的函数/常量层级）。

**工具口径**：
- graphify 在本步**仅用于圈文件范围**——只读 `GRAPH_REPORT.md` 的 God Nodes / Communities 段定位该业务大致涉及哪些文件，**不用其社区分组结果作业务划分依据**（社区分组是代码结构聚类，不等同业务边界）；不读 `wiki/`。
- 需要用 codegraph 核对符号（callers/callees/node）时，按 `GOVERNANCE_RULES` 的 `business-rule.md`「codegraph 查询口径」执行。

## 产出

业务前缀 + 文件清单 + 链路清单 + 页头块，写到批次目录 `step1-overview.md`。

## 注意

- 前缀不得与已有页重复（grep `DATA_BUSINESS` 下各页）。
- **产出只含四项**（业务前缀 / 文件清单 / 链路清单 / 页头块）：核实过程、依据、分歧一律进回执，不写进产出文件（见 `GOVERNANCE_RULES` 的 `business-rule.md` 五「推导过程不进规则文档」）。
- **链路清单每条链路必须附「分链路依据」**：说清触发时机、输入、失败后果，以及「上一张表的输出是不是下一张表的输入」——这段依据是步 3 归类与出图共同依赖的判断载体，不是可选项。
- **页头「不管什么」新增标准排除句**，框架名取 `DATA_PROJECT_FACTS` 的「标准排除句用词清单」，逐业务照抄，不必每次重新论证：
  - `有概览`：按 `GOVERNANCE_RULES` 的 `business-rule.md` 八的指引行格式写 `业务代码调用的第三方框架（<用词>）内部实现 → 见 [第三方框架机制](../overview.md#核心流程)`（业务页在 `DATA_BUSINESS`、`ENTRY_OVERVIEW` 分处不同目录，两者相对路径对全部业务页固定一致）。
  - `无概览`：链接目标不存在，按 `business-rule.md` 八「找不到对应目标时不得写指引行」，写成不带链接的一句：`业务代码调用的第三方框架（<用词>）内部实现，不归本业务`。
- 页头「不管什么」写错会让步 3 归错。
- 页头里指向另一业务的指引行，按 `business-rule.md` 八选链接目标；对方没有页、又 `无概览` 时，不写指引行，按八的兜底写法交页尾「未闭合边界」。
- 页头指引行的链接目标按**最终页**在 `DATA_BUSINESS` 下的位置写（如 `../overview.md#核心流程`），因为这一行最终要原样搬进业务页；产出落在批次目录，这些链接在草稿里点不开是预期行为——不要为了「点得开」把链接改成按批次目录算的相对路径，否则步 6 组装搬进业务页时链接反而是错的。

## 通过判据

人工审核通过：产出四项（业务前缀 / 文件清单 / 链路清单 / 页头块）齐全；前缀未与已有页重复；页头「不管什么」含标准排除句。
