# 全局概览(overview)· 规则与标准

> 本文件只放定稿的规则与标准(结构 / 呈现格式 / 判据 / 边界)。
> 执行流程见 `GOVERNANCE_FLOW` 的 `overview-init.md`(初始化,一次性)与 `GOVERNANCE_FLOW` 的 `overview-sync.md`(业务页组装收尾同步动作)。
> 排除清单见 `DATA_OVERVIEW_EXCLUDE`(定义见 `ENTRY_PATHS`)。

## 一、概览页是什么

- `ENTRY_OVERVIEW` 是项目全局索引页,只放锚点(定位信息 + 一句话描述),不放内容本身;内容永远在业务规则页或代码里。
- **产出位置在 `DATA_BUSINESS`**:本体系是全部规则与最终页面的唯一来源(规则在 `GOVERNANCE_RULES`、流程在 `GOVERNANCE_FLOW`、业务页面在 `DATA_BUSINESS`);业务规则页最终产出同样落 `DATA_BUSINESS` 下 `<业务id>.md`(见 `GOVERNANCE_FLOW_INIT` 的 `step6-assemble.md`)。概览在 `ENTRY_OVERVIEW`、业务页在 `DATA_BUSINESS`,两者分处不同目录,"已建页"判据(见四)以 `page:` 字段指向的文件真实存在为准,不依赖二者同目录。
- 一个项目只有一份概览页。
- frontmatter 字段沿用项目其余业务页同款:`title`/`type: overview`/`status: evergreen`/`updated`/`tags: [overview]`;重建/更新时把 `updated` 刷新为当次日期,不新增额外字段。`title` 取"<项目名> 全局概览"(如本项目为"agentmemory 全局概览"),项目名取仓库目录名或承载文档自称的项目名。
- **本页不是给人逐字阅读的,但条目本身要能点击跳转**:除"项目架构"节的概述性文字外,条目行只放"中文名称 + 一两句描述"供人一眼扫过;除四节 `kind:rule` 行的跳转链接外,链接目标路径、代码路径、文件名等定位信息一律藏进 HTML 注释(`<!-- ... -->`),Markdown/Obsidian 阅读视图不渲染注释内容,人不需要逐字看到,AI(或脚本)读取源文件文本时能读到即可。**08-23 二版改造第 4 条的原意是排版诉求**(定位信息不显示在可见文本、AI 能读到即可),条目本身应保留可点击跳转;此前把"定位信息进注释"落地成"条目本身不可点击"是对该拍板的误读,本次是纠正误读、回归原意,不是推翻既有拍板。核心流程中 `kind:rule` 行(`page:` 字段非 `none`)的中文环节名本身包成 Markdown 链接跳转到该规则页(格式见四),链接目标路径与注释 `page:` 字段保持一致,两处各司其职(链接给人跳转、注释给机器读取),不冲突。

## 二、固定结构:四节,顺序不可变

1. `## 项目架构`(锚点,不算分组)
2. `## 核心流程`(概览主体;按六条核心流程运行顺序逐环节列行,规则页行与配件行混排;规范见四)
3. `## 登记页`(锚点,不算分组;只放两行链接——契约面、配置面;规范见五)
4. `## 未分类`(锚点,不算分组)

不多不少,顺序不可换(项目架构在最前,先给最粗方向;核心流程是主体,紧随其后;登记页轻量,收在核心流程之后、未分类之前)。**"核心流程"是概览唯一的分组层级**:原"业务组"/"框架组"两组并列的结构已撤销,业务专属逻辑与系统级配件按运行时先后顺序混排在同一批流程行里,不再分两组登记;核心流程节内部是否要再细分(如按流程分小标题),按四节判据执行;不允许在"项目架构"/"核心流程"/"登记页"/"未分类"之外另开新的分组维度。

## 三、项目架构节:三态写法

判据按顺序取第一个成立的:

1. **有承载文档**(项目根 `CLAUDE.md`/`README.md`/`ARCHITECTURE.md` 等,已含"技术栈 / 目录分工 / 启动测试方式 / 跨文件结构"中至少一项):可见文本写一句概述("技术栈/目录分工/启动测试方式/跨文件结构见承载文档"一类的一句话,不展开复述),承载文档的相对路径藏进注释:`<!-- doc:<相对路径> -->`。同时有多份都满足门槛的候选文档时,优先选文档自身声明为"入口锚点/唯一入口/开工先读"一类的那份;都没有这类自陈,选四项覆盖最全的一份;只记一份路径,不并列多个。
2. **无承载文档,但内容可在几分钟内盘点清楚**(读 `package.json`/`pyproject.toml`/入口文件即可):直接内联写"技术栈 + 目录分工 + 启动/测试命令 + 一句话整体结构"四项,这是内容本身不是定位信息,照常可见,不加注释;如内联描述中确实带出具体文件路径,把路径部分挪进注释。
3. **都没有**:写 `(未整理:技术栈/目录分工/启动与测试方式/跨文件结构,建议下次概览维护时补齐)`,不阻塞其余三节先落地,无需注释。

判据:
- 状态 1,注释里的路径必须真实存在。
- 状态 2,可见内容至少覆盖四项(技术栈/目录分工/启动测试方式/跨文件结构)。
- 状态 3,文案必须出现"未整理"字样,不能留空行冒充已完成。

### 全局架构图

紧跟三态文字之后加一个 `### 全局架构图` 子节,按 `GOVERNANCE_RULES` 的 `diagram-rules.md` 出一张 SVG("怎么画"见 `sum-svg-diagram` skill),正文只留一行链接,规范见十。这张图画的是**项目由哪些运行时组件构成、组件间以什么方式交互**——组件级技术拓扑视图,不下钻业务在会话生命周期里具体如何触发、按什么条件分支;那是下一个子节"全局业务图"的职责。一项目一张,存 `DATA_IMAGES` 下 `architecture-overview.svg`。

### 全局业务图

紧接全局架构图之后加一个 `### 全局业务图` 子节,按 `GOVERNANCE_RULES` 的 `diagram-rules.md` 出一张 SVG("怎么画"见 `sum-svg-diagram` skill),正文只留一行链接,规范见九。这张图画的是**业务在一次会话生命周期里如何相互触发、传递、回流**——不是核心流程内部的分组关系图(各环节的归属信息已在核心流程节的行文字里,不需要用图重复)。**只画一张整体图,覆盖全部已知业务**(呼应"一项目一张"的既有偏好)——概览是全局视角,业务页流程图是局部视角,两者呈现方式不要求一致。一项目一张,存 `DATA_IMAGES` 下 `overview-flow.svg`(文件名沿用既有约定,未随本节更名而改)。

## 四、核心流程规范

### 4.1 位置与结构

核心流程是概览的主体:按运行时先后顺序列出全部核心链路,每条链路按环节顺序逐行列出,环节顺序由人定(这是概览里唯一需要人判断的部分)。原"业务组"/"框架组"两节撤销,业务专属逻辑登记为规则页行(`kind:rule`),系统级配件登记为配件行(`kind:part`),两者按运行顺序混排在同一批流程行里,不再分成两个独立分组。

**流程表**(登记每条核心流程的序号、名称、首环节;条数与名称由项目实测决定,不预设固定值——下表只给列结构,`流程`/`首环节` 两列的具体值按项目实测填):

| # | 流程 | 首环节(即入口) |
|---|---|---|
| 1 | `<流程中文名>` | `<该流程第一个环节的入口锚点,见 4.2>` |
| … | … | … |

**一行格式**(每条流程下按环节顺序逐行列出;定位信息进 HTML 注释,沿用现行排版约束):

```
- **<环节中文叫法>**[(链接)] — <自定义|框架> · <一句话:管什么>。<!-- kind:<rule|part>; sym:<限定名>; path:<本项目文件路径>; impl:<框架实现位置|none>; page:<规则页相对路径|none>; tier:<骨架|细节|none>[; entry:<4.2 六类之一>] -->
```

字段口径:

| 字段 | 取值口径 |
|---|---|
| `kind` | `rule` = 该环节归某规则页管(中文环节名包一层 Markdown 链接跳转到该页,格式与业务页链接同款);`part` = 配件行(判定见 4.3),不建页 |
| `sym` | 限定名,格式同 `business-rule.md` 二.6"代码对照锚点写法",必须能被 `codegraph node` 查到(系统级配件填本项目接入点的限定名,不填框架内部符号) |
| `path` | 本项目文件路径,人读用,不参与机器匹配 |
| `impl` | 框架实现位置(如 `server/.venv` 内包路径与类名,或 npm 包名与 `.d.ts` 位置),仅 `kind:part` 且归属为框架机制时填;自定义配件填 `none` |
| `page` | `kind:rule` 行必填(该规则页相对路径,与 `ENTRY_OVERVIEW` 里链接/注释的实际写法一致);`kind:part` 行填 `none` |
| `tier` | `kind:rule` 行与页内 frontmatter 的 `tier:` 字段同值(定义见 `business-rule.md` 三);`kind:part` 行填 `none`(这是 `part` 行 `tier:none` 的唯一合法长期状态,不受 4.5 约束) |
| `entry` | 入口行专用可选字段,取值为 4.2 六类 `kind`(`process`/`network`/`tool`/`event`/`schedule`/`external`/`other`);凡该环节的 `sym` 满足 4.2 入口判据(控制权从本项目代码之外进入)即填,不限首环节(入口常分散在流程中段,如工具调用、外部事件回调、断开回调;首环节也可能不是入口,如并行管线分叉);非入口行不填该字段 |

同一规则页可在多条流程里出现,概览行只是导航,页本身才是事实源。

### 4.2 入口种类(六类 + 兜底)

判据一句话:**入口 = 控制权从本项目代码之外进入本项目代码的那个符号**。执行者靠这句话判新种类,不必等清单穷尽。用于判断流程首环节行、规则页/配件行页头的 `kind` 取值(六类之下若是配件而非入口,`kind` 仍按 4.1 取 `rule`/`part`,本表只管入口种类细分)。

| kind | 含义 |
|---|---|
| `process` | 进程入口:`__main__`、CLI argv 解析、可执行脚本 |
| `network` | HTTP 路由 / WebSocket / RPC / 传输层连接建立回调 |
| `tool` | LLM function calling 注册、MCP tool、插件注册 |
| `event` | 框架事件处理器注册、订阅、watcher 回调 |
| `schedule` | cron / interval / 定时任务 |
| `external` | subprocess 协议回调、队列消费者、stdin 协议 |
| `other` | 以上都不是,但符合判据 |

某入口若是另一入口的符号链接(同一份代码被系统重复索引成两套节点),不是独立入口,不单独占行,避免同一入口登记两次。

### 4.3 怎么列全(业务候选集三路并集 + 两条不遗漏核对)

**业务候选集 = 入口 ∪ 装配点内部阶段 ∪ 前端**(装配点指下方"会话装配点"配件行锚点对应代码所编排出的内部处理阶段;前端指面向人的客户端代码,项目存在前端代码时单独作为一条流程)。候选集里每一项要么归某规则页(`kind:rule`),要么占一条配件行(`kind:part`),不允许第三种去向。

**配件行判定**(哪些系统级内容占 `part` 行、不建页):按下列信号任一命中即可(不要求同时满足)——

1. **横切复用**:被两个及以上业务复用、自身不构成任何单一业务的处理内容(不带业务专属决策逻辑)。
2. **顶层文档点名**:项目顶层承载文档(见三节状态1/2)明确点出的基础设施域,即便当前只服务单一业务或尚未被复用。
3. **构成事实**:目录/模块本身的构成事实上是框架/运行时/工具性质(不含业务决策表式内容),如会话装配点、配置解析、命令行入口、测试设施等。

某模块同时命中"配件"信号与"顶层文档点名一项业务能力"时,按是否含业务专属决策表式条件→结果逻辑裁决:不含业务专属决策表、服务全部或多个业务的,占配件行;含业务专属决策表的,归规则页(`kind:rule`)。

**两条不遗漏核对(概览收口判据,都是集合比对,不读代码)**:

1. **装配点逐阶段有行**:读会话装配点配件行锚点对应的代码,它编排出的每一个处理单元/阶段都必须对应核心流程里的一行(`rule` 或 `part`);少一个即判概览不完整。
2. **graphify 社区逐个能映射**:先 `graphify update <代码根>` 把图刷到当前 commit(`<代码根>` 见 `business-rule.md`「codegraph 查询口径」),再取 `<代码根>/graphify-out/GRAPH_REPORT.md` 的 Community Hubs 清单,剔除测试、文档、构建配置三类社区,剩余每个社区都必须能映射到至少一条流程行或配件行;映射不上的社区即漏,补行后再核。graphify 不参与业务划分,只做收口比对。

**这两条保证什么**:①保证运行时主链上没有环节缺行;②保证代码簇层面没有整片代码不在任何行的辐射范围内。两者都是"必要条件"式核对,不保证行的顺序正确(顺序由人定,见 4.1)。

**入口列全的方法(两路交叉,辅助发现候选,不是概览完整性判据本身)**:单靠 pattern 扫描列不全——通用模式扫描(如 `@app.`/`APIRouter`/`argparse` 等)未必能覆盖框架特有的注册机制(如通过 direct-function 机制注册的工具/事件回调)。所以列全靠两路独立通道交叉:

- **A 路 · 框架机制驱动的模式扫描**:先读 `DATA_PROJECT_FACTS` 记录的该项目所用框架/运行时,按框架逐个查它的注册/回调机制长什么样,再据此扫描。不是拿一份通用正则表碰运气。
- **B 路 · 装配点通读**:读会话装配点配件行锚点对应的代码,它字面上就是一份可执行的处理链顺序清单(见九),是入口的权威汇集处。

A ∪ B 为入口候选集(先按符号链接去重);A、B 的差集逐条给出理由,用于甄别候选是否确系入口(只在 A 里的、只在 B 里的各写一行理由)——**这一差集核对只用于说明候选是不是入口,不是概览整体完整性的判据**,概览整体完整性判据是上方"两条不遗漏核对"。只在 B 里的(装配点经过但不是入口,即内部处理阶段)按候选集并集规则进核心流程占 `rule` 或 `part` 行,不因"不是入口"被排除出概览。

### 4.4 概览的完整性与业务梳理档次解耦

**"概览完整" = 4.3 两条不遗漏核对全过 + 每行字段齐 + `sym` 限定名非悬空。** 与各规则页当前是骨架档还是细节档**无关**:全部规则页都是骨架档时,概览同样算完整。梳理**深度**由各页 `tier:` 字段表达(定义见 `business-rule.md` 三),不由概览表达。

业务边界由 4.3 候选集归并决定;项目顶层文档点名只作归并参考,不是粒度的权威来源,与候选集归并结果冲突时以候选集归并结果为准。

### 4.5 全量规则页与 `tier:none` 的短暂性

与 4.4 并列的第二条不变量,**管的是覆盖广度**(4.4 管的是深度):

- **核心流程里每一条 `kind:rule` 行都必须有页**,最低档次骨架档;`kind:part` 行不建页,不受本条约束。
- `rule` 行 `page:none` / `tier:none` 只允许在"该业务刚被识别出来、页尚未建"这段时间内存在,是**过渡态不是稳态**;一轮建页动作收口时必须清零。
- 收口判据:核心流程中不存在 `kind:rule` 且 `tier:none` 的行;4.3 两条不遗漏核对全过。
- 后续加深一律走重建(升档 = 重走细节档流程,定义见 `business-rule.md` 三),不在骨架页上增量补分支行。

**这条为什么是硬的**:在"一切改动从业务进"的总纲下,规则页是唯一入口。有一个 `rule` 业务没页,那片代码上的改动就无处可进,所以它不是整洁度偏好,是总纲的承重条件。

配件行不单独建规则页(`GOVERNANCE_FLOW_INIT` 全篇的对象是"一个业务",配件行不适用);配件代码里带业务语义的出口,由实际调用它的规则页收录。**配件行只做导航与 anchor 登记,不承载规则编号映射**:不新增任何反查用的规则编号字段,不建任何形式的"框架代码 → 规则编号"预存映射——本体系不存在"从代码反查规则"的场景(一切改动从业务页出发),预存映射需要跟随框架改名、编号废弃、页升档重建三种情形同步漂移,收益抵不过维护成本。

## 五、登记页节

登记页是概览的第三种对象,只有两张:**契约面**(记录本项目对外/跨进程契约,如消息协议、命令行契约、任务派发契约等)、**配置面**(记录本项目全部配置项:键名、默认值、缺省行为归属)。

- 一行格式沿用规则页/配件行同款注释字段(`page:`/`sym:`),链接指向对应的契约面/配置面页面。
- 页型:契约面、配置面两张登记页的 frontmatter 均为 `type: registry`。
- 判齐口径:条目列全 + 锚点非悬空 + 归属逻辑页非空(每个条目都能对应到管理它的规则页,或指明其本身即登记页收录的独立事实)。
- 工具类/模板类条目若已被某业务规则页收录管理,并入该页,不重复建独立登记页;登记页只保留契约面、配置面两张,不再拆分出第三张。

## 六、未分类节

- 定义:项目内真实存在、**对项目代码功能有实际影响**(参与构建/运行/测试/部署,或被业务/框架代码实际导入引用)、但项目架构/核心流程/登记页三节都套不进的东西。
- **默认排除口径**:凡对项目代码功能没有实际影响的产物,默认视为排除,**不需要预先登记在 `DATA_OVERVIEW_EXCLUDE` 才能跳过**——纯分析/可视化/一次性辅助工具的脚本与中间数据(不被业务代码导入、不参与构建/测试/部署),不论是工具自动生成还是手写代码,都属此类,直接跳过,不进候选。"默认排除"省的是逐条登记的手续,不省判断本身——执行者仍要对项目顶层扫描到的每一项快速判断一次"是否对代码功能有实际影响"(读一眼用途即可,不用深入分析),不能因为"看起来像分析脚本"就不判断直接跳过。
- `DATA_OVERVIEW_EXCLUDE` 的角色:已核实例外的记录簿,不是白名单机制——执行者判定某产物无代码功能影响后可以直接记进清单(附一句理由),供后续执行者省一次重复论证;记录不是定论,后续发现有问题可以推翻重判。真正**判断不了**"是否对代码功能有影响"的情形,才作为不确定项报告、交人确认。
- 范围:**只扫描项目顶层(第一层目录/文件),不做深层递归**。深层内容需要关注的,由业务规则页或专项盘点处理,不在概览未分类节展开。**挂载根目录本身(本页与全部规则/流程/业务页所在的治理目录)不计入未分类**——它是当前正在使用的治理体系自身,不是"项目业务/框架代码"。
- **与"项目架构"节状态 1 的覆盖边界**:承载文档已泛指覆盖的顶层目录(如项目纪律里点名"官方脚手架结构不动"的 源码/测试/评测/脚本目录,或承载文档明确说明用途的目录)视为已覆盖,不重复计入未分类;承载文档逐一点名目录内部分文件、未列全部文件的,视为该目录整体已被泛指覆盖,不要求逐文件枚举;承载文档用 `@其它文件` 语法引用/包含的内容,视为承载文档的一部分,同样算已覆盖;未分类只收承载文档完全没提及、用途不明的顶层产物。**目录级覆盖不穿透到目录内每个具体文件**——目录内如有明显不属于承载文档所述范围的自定义文件(如脚手架目录下后加的一次性脚本),仍按本节判据(含"是否对代码功能有实际影响")单独判断是否计入未分类。
- 项目架构节状态 1 有多个合格候选文档、最终只链接了其中一份(见三)时,未被选中的候选文档视为已被"项目架构"节主题覆盖,不重复计入未分类。
- 扫描后确实找不到归属(套不进项目架构/核心流程/登记页任一节)、且**确认对代码功能有实际影响**的顶层产物,一行一条:`- **<中文条目名/一句话概述>** — <暂不归类的原因>。<!-- path:<路径> -->`。
- **确实没有则写"暂无"**——改口径后,大多数项目的未分类节正常情况下应为"暂无"(纯分析/辅助工具产物已默认排除,真正"有代码功能关联却三节都套不进"的情形并不常见)。

## 七、定位信息判据(贯穿三/四/五/六节)

- 行内注释给出的路径(`doc:`/`page:`/`sym:`/`path:`/`impl:`),只要不是 `none`,必须真实存在;不存在即悬空,不允许留在正文——应改用"未建页"/"未整理"格式或删除该行。
- `page:none`/`tier:none` 或"项目架构"状态 3 不需要做存在性检查(语义上就是未建页/无承载文档)。

## 八、边界(不做)

- 不修改业务规则页自身的决策表/流程文字骨架(六节顺序、编号规则等,见 `business-rule.md`/`assembly-rules.md`);业务页的可读性书写规范见 `business-rule.md` 新增一节,不在本文件重复。
- 不做面向人眼的置灰/图形化区分(颜色/emoji/HTML 样式)——本页条目本就不是给人逐字看的(一),已建/未建靠注释里的 `page`/`tier` 字段供机器判断,不需要视觉区分。核心流程中 `kind:rule` 行的中文环节名做可点击超链接(见四)不受本条约束:链接是跳转入口,不改变颜色/字重/加粗等视觉样式,不构成"已建/未建"的视觉分级;已建/未建的判断依据仍是注释里的 `page`/`tier` 字段,链接有无只是跟随字段同步呈现的另一种形式,不是新增的判断维度。
- **提交统一**:概览与业务页共用同一套提交机制,不使用 `kb.sh`(五子命令均不复用)。一次组装动作(业务页文件 + `DATA_LOG` 追加行 + `ENTRY_OVERVIEW` 对应行同步,若有)在同一次 `git add` + `git commit` 里完成,不拆成多次、不引入除 git 之外的第二套提交机制。
- 不用 Claude Code `/init` 生成或改造 `overview.md`。
- 不改动/补充项目根 `CLAUDE.md` 内容本身。
- 不为概览维护写脚本,手工/LLM 直接改。

## 九、全局业务图规范

## 十、全局架构图规范

图按 `GOVERNANCE_RULES` 的 `diagram-rules.md` 出 SVG(规范见该文件二·3.4——只给"从哪取材"的事实源指向;"怎么画"读 `sum-svg-diagram` skill,母版结构以该 skill 全局架构图母版为准),正文只留一行链接(目标为本页到 `DATA_IMAGES` 的相对路径拼接 `architecture-overview.svg`,写法见 `ENTRY_AGENTS`)。

### 定位与全局业务图的分工

全局架构图画的是**项目由哪些运行时组件构成、组件之间以什么方式交互**——组件级技术拓扑视图,回答"这个项目里有什么、组件间大致怎么连";不下钻业务在一次会话生命周期里具体如何触发、按什么条件分支、拒绝退出到哪——那些业务级流转语义仍是"全局业务图"(九)的职责。两图不互相替代;具体怎么分层、层内节点怎么归属、连线怎么画,由执行者按 `sum-svg-diagram` skill 结构语法当场判断,本节不预设。

### 证据来源

图的证据来源是项目实测事实——代码、配置、运行时组件的实际部署位置(是否在客户端进程内 / 核心会话服务进程内 / 进程边界之外的外部服务)与组件间的真实交互方式,不臆造未经核实的组件或交互。

一项目一张,存 `DATA_IMAGES` 下 `architecture-overview.svg`。
