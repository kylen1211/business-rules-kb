# 业务规则文档规格

## 一、规则是什么
- 一条规则 = 代码的一个出口(分支 / raise / return)+ 走到它的输入条件。代码有几个出口,就有几条规则。
- 一条链路 = 一串决策表,上一张表的输出是下一张表的输入;不同服务的对接也是这样接上,不按代码文件切分。**"输出即输入"不要求是代码里能读写引用的类型化对象**——提示词内容驱动、且能在代码里指出具体触发字符/触发条件的因果关系,同样算一种"输出即输入",不因看不到类型化代码对象就一律判独立链路。
- 决策表 = "条件 → 结果"两列的表格,一行一条规则。
- 一页可以包含多条互相独立的链路。判断"一页该拆几条独立链路"分两步:①先看触发时机、输入来源、产出后果三者是否都不同——都不同即为独立候选;②再检验候选之间"上一条链路的产出是否是下一条链路的输入"(适用上一条判据,含提示词驱动因果)是否成立——成立则合并为一条链路、内部按阶段分步呈现;不成立则各自成链,不因业务概念上相关就强行合并。

## 二、一页规则文档长什么样(按顺序)
1. **页头**:管什么 / 不管什么(一条一行);验证基线 commit 与编号前缀;`tier:` 字段声明本页当前档次(`骨架` 或 `细节`,定义见三节);"动机查无实据不编造,未验证的结论标[待核实],其余不标"。
2. **业务全貌图**(槽位必选,页头之后、流程文字之前):该业务全部链路组合成一张全貌图(SVG),内容取材于该业务"流程文字"节与"决策表"节(证据来源同 `GOVERNANCE_RULES` 的 `diagram-rules.md` 3.3),具体版式由 `sum-svg-diagram` skill 判断;链路内部逐条分支的最细节判据仍见下方流程文字节各自的局部图。槽位固定写标准真链接一行,指向 `DATA_IMAGES` 下 `<业务id>-overview.svg`;内容(占位图或真图)由独立流程 `GOVERNANCE_FLOW` 的 `diagram-draw.md` 决定,组装步骤不判断、不阻塞,槽位本身不得删除。
3. **流程文字**(必选,核心业务逻辑):每条链路上方留一个图槽位,固定写标准真链接一行,指向 `DATA_IMAGES` 下 `<业务id>-<链路名>.svg`(画法见 `GOVERNANCE_RULES` 的 `diagram-rules.md` 指向的 `sum-svg-diagram` skill);槽位内容由独立流程 `GOVERNANCE_FLOW` 的 `diagram-draw.md` 决定,组装步骤不判断、不阻塞。图槽位之下分层分步写——一条链路一层、一步一行,每步标对应表号与中断条件,不写成整段散文。读者看完就知道全貌。
4. **决策表**(每个节点一张):表前一句说清触发点;列 = 条件 + 结果(+ 备注,可选);行之间有重叠时写明先取谁,否则默认互斥穷尽。
5. **共享前提**:被多张表共用的判断单独一条,各表引用,不重复抄。表前缀可用 M(前提)/ D(决策)/ C(构建期),凭写的人判断。
6. **页尾**三节:未闭合边界(没查到的地方一行一条);代码对照(规则编号 → 代码位置,写法见下方"代码对照锚点写法");归档记录(废弃编号的登记,定义见 `GOVERNANCE_RULES` 的 `assembly-rules.md` 二.2)。
   "正文不夹代码名"细化:
   - 定位信息(文件名、代码位置)一律不进正文,只进"代码对照"节。
   - 本项目自己的函数名、类名、私有常量名、字段路径,改写成业务话。
   - 保留原文的三类:环境变量名与取值字面量;第三方框架的帧 / 事件 / 消息类型名与随其传递的标志名;日志标签一类的字面量——这几类是描述该数据流的唯一无歧义名称,改写反而产生歧义,和"不夹代码名"要防的"读者被迫回源码才能读懂"不是一回事。
   - 图(SVG)的标题、副标题与 Footer 说明不受本条约束,可以带定位信息作为图的出处标注。

**代码对照锚点写法**

页尾"代码对照"表固定三列:`规则编号 | 锚点(限定名) | 文件路径`。**锚点 = 裸限定名,不带文件路径前缀,不写行号**;文件路径是独立一列,只供人阅读,不参与任何机器匹配。

| 情形 | 锚点写法 | 例 |
|---|---|---|
| 类的方法 | `ClassName.method` | `DispatchRegistry.add` |
| 模块级函数 | `function_name` | `assemble_pipeline` |
| 一个大函数里住多个节点 | 锚到它调用的**子函数**,格式同上两行 | — |
| 大函数内无子函数可锚 | `function_name` + 一句**定位话** | `run_bot`(客户端就绪回调内的问候语播种判定) |

硬规则四条:
1. 行号一律不进页面任何位置。要定位时现查:`codegraph node "<限定名>" -p <代码根>`。
2. 定位话必须是代码里**唯一可定位的结构特征**(第几个循环、哪个回调、哪个 with 块),不是代码位置的中文改写,也不是业务描述的重复。
3. 每个锚点的限定名必须能被 `codegraph node` 查到;查不到即悬空,按 `overview-rules.md` 定位信息判据同款处理——不允许留在正文,改用定位话形式或删除该行。
4. 图(SVG)的标题/副标题/Footer 不受本节约束(沿用本规格二.6 现有例外)。

**codegraph 查询口径**(任何 codegraph 查询:callers / callees / node / 锚点校验;graphify 读图同样适用):
- **一律带代码根**:`<代码根>` = `DATA_PROJECT_FACTS`「代码位置」登记的路径换算成的绝对路径。写法:`codegraph node "<限定名>" -p <代码根>`(callers / callees / impact / explore 同样加 `-p <代码根>`)、`codegraph sync <代码根>`、`graphify update <代码根>`,报告读 `<代码根>/graphify-out/GRAPH_REPORT.md`,`graphify query` 加 `--graph <代码根>/graphify-out/graph.json`。不带路径时两个工具只认当前目录,会话不在代码仓库里启动时每个锚点都会被判成悬空。登记了多个代码根的,逐个查,锚点在任一代码根查到即不悬空。
- 查询前先 `codegraph sync <代码根>`——只用命令行时索引不随代码自动更新,不刷新会把新代码判成悬空。
- 悬空以输出 `not found` 为准:查不到时退出码仍是 0。
- 「代码索引排除路径」和挂进代码仓库的 kb 目录已在建索引时按官方配置排除(`GOVERNANCE_PREPARE` 第 3 步),codegraph/graphify 的结果不用再手工过滤;不经这两个工具的扫描(`rg`、读目录)仍按 `DATA_PROJECT_FACTS` 的该字段排除。
- 工具安装与建索引见 `GOVERNANCE_PREPARE`。

## 三、怎么算完整(分两档)

> 一页规则有两个档次:`骨架` 与 `细节`。页 frontmatter 的 `tier:` 字段声明本页当前档次,概览核心流程链到本页的 `kind:rule` 行 `tier` 字段同步同一值,两处不一致以页内 frontmatter 为准并当场改概览。
> **概览核心流程里每一条 `kind:rule` 行都必须有页**,最低档次是骨架档;`tier:none`(未建页)只允许在"该业务刚被识别出来、页尚未建"这段时间内存在,不是可以长期停留的状态。
> **初始化一律先做骨架档**;某业务被代码改动触碰、且该改动需要判断分支级行为时,才升到细节档(升档判据见 `GOVERNANCE_FLOW_UPDATE` 的 `step2-scope.md`)。细节档不回退为骨架档;**主动完善内容一律走升档(重走细节档流程),不在骨架页上零敲碎打补分支行**。

**骨架档 · 三条,全过才算完整**

1. **节点齐**:该业务每条链路上,凡判定结果会改变后续走向的判断点,各占一个节点;判定结果不改变走向的不占节点。
   [核对法:对链路涉及的每个符号取 `codegraph` 的 callees,凡被调用且自身含分支的被调符号,必须能对应到某个已登记节点,或在页尾"未闭合边界"节显式记一行"不改变走向"。对不上又没记的,判不通过。]
2. **连线齐**:每个节点至少有一条出边;每条出边的目标只能是本页另一个已登记节点号,或一个已登记终态名。没有出边的节点不存在,指向页外未定义物的出边不存在。
   [核对法:节点表逐行扫出边目标,与节点号清单、终态清单做集合包含检查。纯机械,不需要读代码。]
3. **终态齐**:链路每一个对外可见终态都在页上有名字;**同一去向的多个代码出口合并成一行,合并行必须注明"合并自 N 处"**。
   [核对法:对该业务入口符号枚举其 return/raise 去向,每一个都要能归到某个已登记终态;归不到即缺终态。N 的准确性不核(那是细节档的事),但字段不许缺——升档时就是把这一行拆成 N 行,N 缺失等于把升档需要的信息丢了。]

**细节档 · 三条,原文不动**

1. 每个维度的特殊输入(未设置 / 空 / 非法值)都落进某一行。
2. 任意一组输入只命中一行。
3. 代码出口数 = 规则行数,一一对应;少了补,多了查代码。

**两档的流程差异**(与 `GOVERNANCE_FLOW_INIT` 对应)

| | 骨架档 | 细节档 |
|---|---|---|
| 步 1 概览 | 走 | 走 |
| 步 2 提取(F 号枚举全出口) | **不走** | 走 |
| 步 3 归纳 | 走(只归节点/连线/终态,不编分支行) | 走 |
| 步 4 校验(F 号双向核对,换人做) | **不走** | 走 |
| 步 6 组装 | 走,组装自查加上方三条核对法 | 走 |
| 质检责任 | 组装执行者自查,不换人 | 换人双向核对 |

降低换人核对这道门禁的代价,明写:骨架档漏一个节点,代价是升档时才发现漏了;细节档漏一条分支行,代价是页面对着代码撒谎。两者不同量级,所以骨架档承受得起自查。

## 四、怎么产出
> 本节按三节两档判据分叉:第 2 条、第 5 条各自只适用于其中一档,不通用于两档;骨架档与细节档的完整流程差异见三节"两档的流程差异"表。

1. 写的人直接读代码,不经二手转述。
2. 出口列法按档分叉:
   - **骨架档**:不逐一列全出口,只按三节骨架档三条判据产出——节点齐、连线齐、终态齐(终态可"同一去向多处合并成一行,注明合并自 N 处"),不编分支行、不产出口逐条清单。
   - **细节档**:列出目标代码全部出口(含每个 raise),每个出口写一行:条件 → 结果。
3. 重复的判断合并成共享前提;按执行顺序写流程文字。
4. 编号只增不改,废弃原地标记;跨文档引用只写编号不复述。
5. 验收按档分叉:
   - **骨架档**:组装执行者自查,过三节骨架档三条核对法即算通过,**不强制换人、不核对出口数**。
   - **细节档**:验收 = 换人拿代码出口数核对表行数。

## 五、不进规则文档的内容
修订记录、推导过程、踩坑复盘、对代码行为的产品评价——分别去 git 历史、agentmemory、`pipeline/debts.md`。

## 六、可读性书写规范(适用范围含本规格与 `GOVERNANCE_FLOW` 下全部流程指引)

- 决策表的「条件」「结果」列与流程文字的每一步,主体用可读的中文描述叙述"发生了什么",不用编号本身充当叙述主语(反例:一行只写"D04-01/02/03 任一失败";正例:"临时文件写入失败或子进程创建失败时拒绝(D04-01/02/03)")。
- 需要点出规则编号(`Dxx-xx`/`Mxx`/`Cxx`)方便定位时,编号放在描述之后的括号内,不堆砌超过两个编号在同一括号里——需要引用三个及以上编号时,要么改写描述让它自然覆盖这些前提,要么拆成多个括号分别贴在对应的描述短语后面,不要把编号列表整坨甩在句尾。
- 该原则同样适用于 `GOVERNANCE_FLOW` 下的流程指引文档(步骤说明、注意事项等散文部分):优先讲清楚"这一步在做什么、为什么这么做",机制代号(F 号/D 号/M 号等)第一次出现时给出全称或简短说明,不假定读者已经记得所有编号的含义。
- 例外:`DATA_LOG` 的单行记录、决策表/代码对照/归档记录等结构化表格本身,是压缩过的机器可读索引,不受本节约束(它们的可读性判据是"能否配合页面内容定位",不是"独立成句可读")。
- 该规范目前只约束新写内容;已建页的业务是否需要按此规范回头修一遍,不在写规则本身的范围内,留给下次该业务走更新流程时顺带处理,不单独起一轮改造。

## 七、流程图规范

流程图与业务全貌图统一按 `GOVERNANCE_RULES` 的 `diagram-rules.md` 出 SVG,不再使用 md 内嵌 mermaid;业务全貌图画法见 `GOVERNANCE_RULES` 的 `diagram-rules.md` 3.3。

## 八、页头边界指引与跨链接规范(只约束今后新写的页头)

- 页头"不管什么"条目分两种:**本业务专属边界说明**(除点出"归谁"外还带本业务特有的推理或事实,如某装配顺序为何不下判断)照常写自然语言 + 可选编号引用,不受本节约束;**纯归属指引**(条目全部内容就是"这块内容整体不归本业务管,归某条配件行或另一业务,没有本业务专属的补充说明")才适用本节。
- 纯归属指引条目改写为一行"指引行",格式:`- <一两个词点出这是什么内容> → 见 [<框架类别中文名或对方业务中文名>](<链接目标>)`,不复述对方类别/业务在其权威定义处已有的完整描述。
- 链接目标:
  - 指向某条配件行 → `<相对路径>overview.md#核心流程`(概览"核心流程"是既有二级标题,Markdown/Obsidian 均按标题文本原生生成锚点,无需改概览生成规则;跳转到章节后按环节名就近找到该配件行及其一句话定义与锚点,人工与 AI 均可就近核对)。
  - 指向另一业务 → 该业务已建页真实存在时,直接链接到该页文件本身(整页即该业务权威定义,不用锚点);未建页时退链到 `<相对路径>overview.md#核心流程`(章节级,该业务对应的 `kind:rule` 行含 page/tier 供核对)。
  - 写指引行前先确认链接目标确有对应内容(核心流程里已登记的配件行,或已登记的 `kind:rule` 行);找不到对应目标时不得写指引行,按现状如实描述该内容本身的归属疑问,交页尾"未闭合边界"节,不臆造链接目标。
- 业务之间互指同理,唯一区别是链接目标选取规则(已建页优先,否则退链到 `<相对路径>overview.md#核心流程`)。
- 维护提醒:本业务页头存在指向另一业务"退链到 `<相对路径>overview.md#核心流程`"的指引行,若后续该业务建页,写这次改动的执行者应顺手把链接更新为对方新页路径(不强制阻塞既有页面,新增/更新页头时顺带处理即可)。
