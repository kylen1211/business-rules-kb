# 规则页组装 · 规则与标准

> 本文件只放定稿的规则与标准(用词 / 硬规则 / 模板与临时编号机制 / 边界 / log 记录规则)。
> 执行流程见 `GOVERNANCE_FLOW_INIT`(初始化)。

## 一、用词(只用这五个)

> 本表是本体系全部 md 文件的用词唯一事实源;改动本表(增删词条、改定义、改作废词清单)当次必须同步排查本体系全部 md 文件里受影响的旧用法一并改掉,不留残留。

| 词 | 定义 | 编号 | 页面位置 |
|---|---|---|---|
| 业务 | 一套业务规则 = 一页 | 编号前缀 `SCENARIO`,页头"编号前缀"字段声明一次;不进页内编号 | 整页 |
| 链路 | 业务内一条执行流程 | 不进编号,步骤表表达 | 流程文字节下一链路一小节(图 + 分步) |
| 节点 | 链路上一个决策表 | 页内两段编号的第 1 段 `D02` | 决策表节一个小节 |
| 分支 | 节点一个出口 | 页内两段编号的第 2 段 `01`,与节点段合写 `D02-01` | 表中一行 |
| 前提 | 业务级跨节点共用 | 页内两段编号 `M02`(单段,不挂节点) | 共享前提节 |

**编号写法**:页内正文一律写两段(`Dxx-xx` / `Cxx-xx` / `Mxx`),业务段(编号前缀)只在页头"编号前缀"字段声明一次,不逐条重复;跨页引用(其它业务页/文档指向本页某条编号)时才写全三段,如 `SCENARIO-D02-01`。

作废词:domain、模块、决策点、flow、业务线。

**作废词的合法用法边界**(下列场景不算撞用作废词,可以照常使用;判断口径是"是否被当成'业务/节点/链路'这套规则用词的同义替换"):
- `模块`:编程语言本身的 module 概念(模块顶层语句、模块级测试专用单例等,是对代码事实的客观描述)不受限;文件内部自用的章节序号(如 `GOVERNANCE_RULES` 的 `diagram-rules.md` 的"3.1/3.2……"),以及其它文件对该章节序号的跨文件引用(如某文件写"参照 diagram-rules.md 3.1 判据"),同样不受限。
- `flow`:治理目录本身的路径名 `flow/` 及其相对路径引用(如 `flow/init/`)不受限;正文口语化提及“按 flow 注意事项/flow 文档”指代该治理目录本身,同样不受限;Markdown/mermaid 语法关键字 `flowchart` 不受限。
- 其余三个作废词(domain、决策点、业务线)目前项目内没有已知的合法歧义用法,原则上零容忍;引用"被否决的方案名"本身(如描述"曾考虑过 flows/domains 双目录拆分但未采纳")不算撞用,是在陈述一个被拒绝的历史选项,不是把该词当规则用词使用。后续若发现新的合法边界,比照上述两条的写法在本节补一条,不要绕过表直接在正文里默许。

另有一套**临时编号**(F 号,见三·五),只在步2–步4 内部核对用,不进页面、不是正式用词,不与上表混淆。

## 二、硬规则

1. **编号终身不复用**:只增不改;废弃号不再分配。写 raw 前读当前页取下一号(页即台账,批次串行所以够用)。
2. **页面只显示在用**:废弃行从正文移除,页尾"归档记录"表记 `编号 | 废弃 | change-id | commit`;旧内容查 raw(写后不改)或 git。
3. **质检按档分叉**:核 raw 是否按规定整理(编号两段合法、列齐、链路坐标齐)对两档都适用;质检的具体核对法分叉——
   - **骨架档**:走 `GOVERNANCE_RULES` 的 `business-rule.md` 三"骨架档三条"集合检查(节点齐/连线齐/终态齐),不产 F 号、不做双向核对。
   - **细节档**:核步2 出口清单每条临时编号(F 号)在步3 产出的映射表中有登记、且登记的去处确实存在于 raw 正文 + raw 正文每条 `Dxx-xx`/`Mxx` 至少被一个临时编号引用(防止凭空增加,机制见三·五),换人做双向核对。
   - 两档均不做其它源码级校验。
4. **批次按 commit 串行,先来先改**;变更 raw 每行必须带链路坐标(链路 + 步号),缺的进"不确定"。
5. **一节点一张表,不合并**:样本 D07-D09 合表要拆三张;前期不精简,走完整流程后再议合并。
6. **每表必有编号列,每行两段编号**(`Dxx-xx`/`Cxx-xx`,业务段只在页头声明一次,不逐行重复):单出口节点也写满(`C01-01`);集合/登记表每行一个分支号;样本 D01 补编号。
7. **图必占位,判断不入建页流程**:四类图(链路局部图 `GOVERNANCE_RULES` 的 `diagram-rules.md` 3.1、全局业务图 3.2、业务全貌图 3.3、全局架构图 3.4)槽位一律不得删除——组装步骤(`GOVERNANCE_FLOW_INIT` 的 `step6-assemble.md`、`GOVERNANCE_FLOW` 的 `overview-init.md`)统一写标准真链接一行,指向约定文件名(`DATA_IMAGES`,命名见 `GOVERNANCE_RULES` 的 `diagram-rules.md` 五);链接目标文件此刻若不存在,组装步机械复制 `sum-svg-diagram` skill 的 `assets/placeholder-pending.svg` 到该文件名占位。要不要画、什么时候画、怎么画,建页/概览流程一律不判断、不阻塞,全部移交独立流程 `GOVERNANCE_FLOW` 的 `diagram-draw.md`(不占编号,随时可触发,可独立重跑用于补图或重画)。

## 三、模板:只锁骨架,不锁列

六节顺序固定:页头 → 业务全貌图 → 流程文字 → 决策表 → 共享前提 → 页尾(未闭合边界 + 代码对照 + 归档记录)。
每个节点一张表、按编号排;**表的列由写的人定**(样本实测三种:条件表 / 矩阵表 / 登记表,强行统一会失真)。

| 槽位 | raw 来源 |
|---|---|
| 页头(管/不管/基线/`tier:`) | 页头块(`tier:` 声明本页当前档次,`骨架` 或 `细节`,定义见 `GOVERNANCE_RULES` 的 `business-rule.md` 三) |
| 业务全貌图 | 组装步机械占位真链接(文件不存在时复制 skill 占位资产补位),图内容由独立流程 `GOVERNANCE_FLOW` 的 `diagram-draw.md` 产出,正文只留一行链接(`GOVERNANCE_RULES` 的 `business-rule.md` 二.2、`GOVERNANCE_RULES` 的 `diagram-rules.md` 3.3) |
| 流程文字 · 每条链路 | 步骤表(链路 \| 步号 \| 说明 \| 引用编号 \| 中断) |
| 流程图 | 组装步机械占位真链接(文件不存在时复制 skill 占位资产补位),图内容由独立流程 `GOVERNANCE_FLOW` 的 `diagram-draw.md` 产出,正文只留一行链接(规则 7) |
| 决策表 · 每个节点 | 节点表(节点号 \| 触发点 \| 列定义 \| 各分支行) |
| 共享前提 | 节点表中 M 号 |
| 未闭合边界 | 待核实表 |
| 代码对照 | 分支行的锚点(限定名)列 + 文件路径列(写法见 `GOVERNANCE_RULES` 的 `business-rule.md` 二.6"代码对照锚点写法") |
| 归档记录 | 变更表中状态=废弃的行 |

### 三·五、出口临时编号机制

**本机制仅适用细节档**:骨架档不走步 2(提取)与步 4(校验),不产 F 号、不产映射表,下方 1–4 条全部不适用骨架档(骨架档的核对法见 `GOVERNANCE_RULES` 的 `business-rule.md` 三"骨架档三条")。

用来把硬规则 3 的"每条出口有明确去处"变成可机械核对的判据,替代失效的"总数相等"判据。

1. **编号规则**:步2 按步1文件清单内函数出现顺序编 F01、F02……;函数内每个出口按代码顺序编两位分支号,如 `F16-03`(第 16 个函数第 3 个出口)。**无出口的函数(如只做赋值的 `__init__`)同样占一个 F 号,行内标"无出口",不产出口行**——保证 F 号与文件内函数一一对应,核对时不疑漏号。F 号只在步2–步4 内部流转,不进最终页面。**三类扩展对象按同一判法各占一个 F 号**:类定义(含无方法体的 frozen dataclass、只有 docstring 的自定义异常类)与函数同等对待,无出口的同样标"无出口";类里单独定义的方法(如 `__repr__`)另占一个 F 号,不并进类本身那一号。模块顶层语句(不在任何函数体内、import 期执行的调用或赋值,如顶层自检调用、顶层配置加载)各占一个 F 号,行内注明"模块顶层语句,非函数";它们确实产生出口(抛异常 / 正常通过),按出口照常编分支号。被符号级圈定的函数体内片段(步1文件清单只圈了某函数的一部分,而非整个函数)同样占一个 F 号,行内注明是片段、函数其余部分不在范围内不枚举其出口;片段内含可传播异常的调用则按出口编分支号,纯读值、无异常路径的片段标"无出口"。判断片段是否算"有异常路径"的口径:片段内调用的目标若本身已在本次提取范围内单独占了 F 号并枚举过出口,该调用不在片段这一号里重复计;片段本身没有字面的 `raise`/`return`/`assert` 语句时标"无出口"。
2. **步2 只列结构性事实,不做判断性标注**:每行前加 F 号列;描述"是否在循环体内 / 是否被恒定收尾包裹 / 是否是隐式 else"这类结构事实,不用"独立出口"/"非独立出口"这类需要归纳判断才能下的结论——是否算一条正式分支行是步3 的事,步2 越权预判会和步3 实际归类打架。
3. **步3 产出"临时编号映射表"**(F 号 → 去处),去处限定五种封闭类型,不许自造第六种:
   - ① `Dxx-xx` 分支行
   - ② `Mxx` 前提段
   - ③ 节点"触发点"文字段
   - ④ 节点"备注"文字段
   - ⑤ 节点"恒定收尾"文字段
   允许一对多(1 个 F 号拆进多个 `Dxx-xx`,如一次异常判定拆成三个 degraded 分支)和多对一(多个 F 号合并进同一个 `Mxx`,如三个无分支构造函数合并成一条前提说明)。
4. **步4 双向机械核对**(换人做,不由步3执行者做):
   - 正向:每个步2 F 号在映射表中出现,且登记的去处在 raw 正文里真实存在 → 通过;缺失 → 回步3 补映射,或回步2 核实是否误列。
   - 反向:raw 正文每条 `Dxx-xx`/`Mxx` 至少被一个 F 号引用 → 通过;零引用 → 判定"疑似凭空增加",回步3 核实源出口或删除该行。
   - 两项全过 = 通过;任一项不过 = 不通过,回步3,本步不改任何内容。

## 四、边界

**不做 / 搁置**
- flows/domains 双目录拆分。以业务规则单页形态(见 `GOVERNANCE_RULES` 的 `business-rule.md`)为准。
- 源码级质检,出口去处完整性核对除外(规则 3)
- 表的精简合并(规则 5)

**归属判定精细化**

文件跨两个业务时按节点/符号粒度判断,不按文件整体交人定,理由:文件是物理容器,不是规则单位;两个业务共用同一文件但各自只消费文件内互不重叠的一部分符号(常量/函数/类)时不构成规则冲突,只需各自登记本业务实际用到的符号即可,不必整个文件判"不确定"。真正需要交人定的是**同一个节点本身**跨业务共用、无法拆分——两个业务要落页的内容互相依赖对方分支的判断结果,任何一方脱离对方都写不清自己那条规则。

**再细化**:判断"同一节点跨业务共用"不能只看"函数体是否可物理拆分"——这只是必要条件,不是充分条件。真正的判据是**各自要落页的内容是否依赖对方分支的判断结果**:依赖→交人定;不依赖(即便物理上写在同一段代码里)→各自记各自的常量事实,不进待核实表、不新开对方业务的 D/M 号。已核实案例见经验记录 `DATA_LESSONS`「函数体不可拆但双方各记常量事实」条目。

**遇到即停、交人定**
- 同一节点(函数体内的分支/顺序判断)被两个不同业务的链路共同决定、无法拆成独立节点分别归属
- 业务内一节点被两条链路共用
- 废弃号被其它链路或前提引用
- diff 触及的文件不在任何业务清单
- 本业务某分支是否存在/可达取决于框架内部机制、静态无法确定(收窄:框架内部实现细节本身不算"数不清"、由步1"不管什么"标准排除句直接排除,不进这张表;只有影响本业务规则内容本身的可达性疑问才进,如"某回调是否会被多次触发"这类)

## 五、log 记录规则

log 是本体系新增数据与变更的记录枢纽,必须有;当前阶段只做简单记录——**一条流程(初始化或更新)走完才追加一条**,不记中间状态。四节"遇到即停、交人定"命中时整条流程停手待人定,不产出页面变更,当次不追加 log(等真正走完再补记一条)。

### 5.1 沿用 `DATA_LOG` 现有格式,不另起炉灶

不改现有 frontmatter 结构、不改排序方向、不改单行语法:
- frontmatter 六字段不变;**每次追加同时把 `updated` 刷新为当次追加日期**。
- 正文"Newest completed operations appear first":新条目插在 `# Wiki Log` 标题正下方(最上),不追加到文件末尾。
- 单行语法不变:`- YYYY-MM-DD — <type> — <一句话>`。
- 权威 log 文件是 `DATA_LOG`。

### 5.2 三个专属 type:`rule-init` / `rule-update` / `rule-retire`


一次性治理动作(如清页、迁移,不是"某业务走完一次初始化/更新")不占用这两个 type,自由命名(不做枚举),只需遵守 5.1 的行格式,不受 5.3 字段清单约束;这类条目的 `commit:` 字段口径按 `ENTRY_AGENTS`“commit 与事后事实记法”执行(通常是记录自身所在的这次提交,用自指写法),与下方 5.3 表格 `rule-init`/`rule-update`/`rule-retire` 三个专属 type 的 `commit:` 字段(写入当下已知的基线 commit,直填真实值)是两种不同语义,不要混用写法。

业务页经 `GOVERNANCE_FLOW_UPDATE` 走完一次治理重审触发的更新、但 D/M 编号无新增无废弃(纯链路重组/呈现调整)的情形,同样不强套 `rule-update`——`rule-update` 的核心信息量在于编号列(5.3),没有编号变化时套用只会产生"新增:无;废弃:无"这种无信息量的行;这类条目按自由命名处理(建议沿用 `kb-governance`,与其它治理性 log 条目风格一致),`commit:` 字段仍按自指写法(与本条同批提交时)。

### 5.3 一行只记关键信息 + 状态必须写清

raw 写后不改、页面组装自查已有全部数字,log 不重复抄内容;但**新增 / 更新 / 作废三种状态必须在行内看得出来**,靠 type 加编号列表达:

| type | 何时 | 行内状态写法 |
|---|---|---|
| `rule-init` | 业务页首次建成 | 新增整页,不列编号(全在 raw) |
| `rule-update` | 业务页一次更新 | `新增:<编号列>;废弃:<编号列>`,只写编号不写内容;无则写"无" |
| `rule-retire` | 整页或整条链路作废 | `废弃:<页名或链路名>` |

行格式:`- <date> — <type> — <业务>:<一句话结论>;<状态>;raw:<raw 路径>;commit:<基线 commit 或 change-id>`

示例:`- 08-30 — rule-update — BR-DISPATCH:超时改为可配置;新增:D04-05,D05-04;废弃:D04-02;raw:data/business/raw/update-chg-0012/;commit:abc1234`

链路名、节点/分支/前提计数、分支内容不进 log,查 raw 与页面(组装自查 / 归档记录)。

### 5.4 何时追加、谁追加

- 初始化:步6(组装,机械执行者)在生成 `DATA_BUSINESS` 下 `<业务>.md` 之后、`git commit` 之前追加,与既定顺序"生成页面 → 页头基线commit → log 追一行 → 概览同步(`GOVERNANCE_FLOW` 的 `overview-sync.md`)→ 一次 `git add <挂载根>` + `git commit`"一致(见 `GOVERNANCE_FLOW_INIT` 的 `step6-assemble.md`),本节只补全"追一行"的格式。
- 更新:步4(组装,机械执行者)与其余关联项(步骤行/代码对照行/页头基线/归档记录/概览同步)同批同步追加,不单独起一次操作,随同一次 git 提交落地。

### 5.5 与硬规则 2/4 的衔接

- 硬规则2(编号只增不改,废弃行入页尾"归档记录"表):log 的 `rule-update` 条目不逐条复述废弃编号明细,只给计数,详情以页面表为准;log 条目的 change-id/commit 应与页面归档记录表对应行的 `change-id | commit` 两列一致,交叉核对靠这两个字段对齐,不是靠复述编号明细。
- 硬规则4(批次按 commit 串行,先来先改):log 更新条目的追加顺序即处理顺序即 commit 时间顺序,与 log"最新条目在最上"的展示顺序天然吻合,不需要额外排序动作;若同批 diff 触及两个业务(更新步1"拆成两批"),按业务拆成两条独立 log,各自的链路/编号范围只记本业务部分,change-id/commit 两条相同。
