# 步 2 · 定范围与分流

判断类,单独做,人审后才进下一步。总则见 [`README.md`](./README.md)。

本步在**开发验收之后**执行,和步 1 之间隔着整个开发周期。

## 范围

两件事,顺序不可换:

**其一,定受影响范围。** 从本次改动的 diff 出发,定清楚动了哪个业务、哪些链路、哪些节点。判定"受影响节点"的口径是封闭的五条,命中任一条即算受影响:

1. 该节点任一分支行的条件或结果,其所指的代码行为发生了变化;
2. 该节点新增或废弃了分支;
3. 该节点整个新增,或整个废弃;
4. 该节点的触发点 / 备注 / 恒定收尾文字段所描述的事实发生了变化;
5. 某条共享前提(`Mxx`)的内容变了——此时把现有页上引用该前提的**全部节点**一并计入受影响集合,因为前提变了那些节点的实际规则就变了。

只有代码位置行号漂移、而条件与结果所指行为完全不变的节点,**不算**受影响(行号更新在步 6 随代码对照节顺带同步)。

**其二,做一次分流判定。** 用 [`step6-assemble.md`](./step6-assemble.md)"分流判据:局部改 vs 废弃新建"节定义的三条线逐条算,得出"局部改"或"废弃新建"。判据全文放在步 6 是因为它在收口时还要复核一次,两处用的是同一套判据、同一份定义,本步不另立一套。

- 判定为"局部改" → 继续步 3。
- 判定为"废弃新建" → **本流程到此终止**,不做步 3–6,不产出页面类改动;按 [`../README.md`](../README.md)"停止交回格式"整理判定依据,交回入口分诊重新判断——本流程不自行断言"转初始化",也不直接指派后续执行者。

## 产出

1. 受影响坐标清单:业务 id / 链路名 / 受影响节点清单(列 `Dxx` 号,新增节点先标"待编号")+ 每个节点命中上述五条口径的哪一条。
2. 分流判定表:三条线逐线写"命中 / 未命中"及其依据(数字或条目名),最后给结论。**只给结论不给逐线依据的,视为本步未完成**——判据要能复现,依据不写下来就复现不了。
3. 若结论是"废弃新建":一句话交回说明(为什么本流程判定处理不了,附三条线命中哪一条与依据),交回 [`../README.md`](../README.md) 入口分诊,不指定后续由谁执行、走哪条流程。

## 注意

- **diff 触及的文件不在任何业务清单里 → 不确定,停下交人定**(`GOVERNANCE_RULES` 的 `assembly-rules.md` 四"遇到即停")。**这条是异常兜底,不是正常路径**:本体系的总纲是"一切改动从业务进"(见 `../README.md`"从业务页出发的核对动作"),正常流程执行者在动代码前已经按那六步定位过业务与编号,走到本步时业务早已明确,理应走不到这条判据;真走到了,说明这次改动没有从业务页出发(如接手他人改动、回溯历史提交),按下列"补页"动作修复,不是本步该自行判断的分歧——**修复动作**:交人定后,若确认该文件片段确实不属于任何已登记业务,按业务认定信号重新识别归属并先建骨架页(见 `GOVERNANCE_RULES` 的 `overview-rules.md` 四·4.5"全量规则页与 `tier:none` 短暂性"不变量),让同一片代码下次有业务入口可进;骨架页建成后再回到本步继续。
- **一次 diff 触及两个业务 → 拆成两批**,各自走一遍本流程,各自记各自的 log 条目,两条 log 的 change-id / commit 相同(见 `GOVERNANCE_RULES` 的 `assembly-rules.md` 5.5)。
- 受影响节点清单宁可宽不可窄:多列一个节点的代价是步 3 多读一段代码,漏列一个节点的代价是页面留下一条与代码不符的规则,后者严重得多。
- 本步只定范围,不读出口、不动编号、不看草稿——**看草稿会污染范围判断**:草稿写的是"打算做什么",范围要按"代码实际动了什么"定,两者的差异正是步 6 要核对出来的东西,在本步就把它们混在一起,步 6 的核对就失去意义了。
- 分流判定命中即停:三条线按顺序算,任一条命中就是"废弃新建",不必再算后面的线。

## 通过判据

人工审核通过:受影响坐标清单每项都有链路坐标(链路 + 步号,硬规则 4);每个受影响节点标明命中五条口径的哪一条;分流判定表三条线的依据齐全且可复算;结论为"废弃新建"时本流程终止、不产出步 3 及之后任何产物。
