# 规则页组装 · 更新流程总则

> 规则与判据见 `GOVERNANCE_RULES` 的 `assembly-rules.md`;页格式见 `GOVERNANCE_RULES` 的 `business-rule.md`;散文部分的可读性写法(编号不当叙述主语,统一放关键词后括号内)见 `GOVERNANCE_RULES` 的 `business-rule.md` 六。
> 初始化流程(一个业务第一次建页)见 `../init/README.md`,本流程不重复其作业方法,只引用。

目标:一次业务代码改动落地后,把已建成的业务规则页更新到与当前代码一致,且这次更新的规则内容与开发动手前定义的规则草稿逻辑一致。

## 从业务页出发的核对动作(总纲:一切改动从业务进)

**本体系的入口方向只有一个:业务页 → 代码,不反向。** 正常开发、规划、bug 修复都先打开业务规则页核对规则,再看代码。下列六步是一次改动的标准动作序列,发生在"什么时候走本流程"判定之前——先按六步核对完,再决定是否需要触发下方六步组装流程(通常只有"升档判定"这一支才会真正启动步 1–6 的整页更新;其余情形就地按骨架档判据更新或按细节档改现有页,不必每次都跑一遍整条流程):

| 步 | 动作 | 产出 / 判据 |
|---|---|---|
| **1 · 定位业务** | 打开概览:**按流程找**——先定本次改动在六条核心流程的哪一条、哪个环节,顺该行链到页 | 得到页清单。落在 `kind:rule` 行但页不存在 → 说明该业务尚未建页,先按骨架档建页再回本步(修复动作,不排队);落在 `kind:part` 行(配件行)→ 顺锚点现查代码,改完只更新该行的锚点与一句话,不建页 |
| **2 · 定位编号** | 在该页读流程文字与决策表,定位本次要动的 D/M 号 | 得到编号清单。这是人与 AI 的共同核对物:双方都在这几个编号上说话,分歧必须落到编号上 |
| **3 · 顺锚点到代码** | 拿编号在页尾代码对照表取限定名 → `codegraph node "<限定名>" -p <代码根>` 取当前位置 → 读代码 | 到达代码。查询口径见 `GOVERNANCE_RULES` 的 `business-rule.md`「codegraph 查询口径」 |
| **4 · 改代码** | 按第 2 步定好的规则改 | 规则先行:开发期间任何规则调整只改草稿,不改正式页(见 `step1-draft.md` 现有机制) |
| **5 · 改完核对** | 只核对第 2 步列出的那几个编号:页上写的条件→结果,与改完的代码是否一致 | **核对范围就是那几个编号,不重读全页、不重画图**。一致 → 收口;不一致 → 改页或改代码,二选一并记原因 |
| **6 · 升档判定** | 判该页是否需要从骨架档升到细节档 | 见下方四支封闭判据 |

**升档判定(四支,封闭)**

- 页为 `细节` → 照现行 update 六步走,不涉及升档。
- 页为 `骨架`,本次改动**只改变节点间连线或终态集合**(增删节点、改走向、增删终态)→ 就地按骨架档判据更新,**不升档**。
- 页为 `骨架`,本次改动**改变某个节点内部的分支行为**(同一节点在不同输入下的结果变了、加了一个新的输入维度)→ **升档**,该页按细节档流程重做一遍(即触发下方 step1–step6 全套),本次改动的更新并入升档那一次。
- 页为 `none`(未建)→ 按步 1 的修复通道先建骨架页。

不留"执行者觉得需要就升"的口子:升档是本体系最贵的动作,触发条件必须是可复核的事实(改的是连线还是分支内容),不能是主观感觉。
**与"完善"的区分**:上述四支说的是**跟随代码改动**的处理;**主动完善内容**(代码没动、只是想把某页写深)一律直接走升档/重建,不适用"就地更新"那一支。

**本流程不引入任何从代码 diff 反查规则的步骤**——上述六步方向唯一(业务页 → 代码)。正常情况下,进入本流程(细节档页的六步组装)之前,执行者已经通过上方六步的第 1/2 步知道了业务与受影响编号,`step2-scope.md` 的定范围动作只是把这份已知信息坐实成"受影响坐标清单"这一正式产出,不是重新从 diff 反查规则;`step2-scope.md` 里"diff 触及的文件不在任何业务清单"那条判据,前提是"从 diff 出发、事先不知道业务",与总纲相反,已降级为异常兜底,详见该文件"注意"节说明。

## 什么时候走本流程

按 [`../README.md`](../README.md)"入口分诊"判定进入本流程(业务页已存在);从 step1 还是 step2 开始、触发源怎么标注,同样见入口分诊页判据2,本文不重复。

**本流程只对自己负责**:执行中途发现改动规模已达"整页重来"量级(判据见 [`step6-assemble.md`](./step6-assemble.md)"分流判据"节),本流程到此停止,不产出步 3 及之后任何产物,按 [`../README.md`](../README.md)"停止交回格式"交回入口分诊——是否转 init、什么时候转,由入口分诊页判断,本流程不自行断言目标流程、不直接联系另一条流程的执行者。

## 与初始化的关系:不重复发明作业方法

提取(读代码列全部出口)、归纳(分节点 / 抽共享前提)、校验(临时编号双向核对)这三件事的通用做法已在规则里定稿,本流程直接引用、不重讲:

- 出口临时编号机制(F 号):`GOVERNANCE_RULES` 的 `assembly-rules.md` 三·五
- 硬规则 1(编号终身不复用)、3(质检只核格式 + 出口去处完整性)、4(批次按 commit 串行、每行带链路坐标):`GOVERNANCE_RULES` 的 `assembly-rules.md` 二

本流程只负责讲清楚**更新场景特有的四件事**,这四件事初始化流程里没有、也不可能有:

1. 开发动手前先定义规则草稿(初始化是事后从代码抽,更新是事前先定规则)。
2. 范围如何限定到受影响节点(初始化是整页从零做,更新只做被改动碰到的那一部分)。
3. 如何与现有页 diff,新增 / 废弃编号怎么处理(初始化的页是空的,没有 diff 对象)。
4. 组装结果如何与草稿核对、不合格如何打回、改动大到什么程度就不局部改而整页重做。

## 规则先行与"强制锚定"

产品 / 开发动手写代码前必须先有规则草稿(步 1),开发期间的任何规则调整都只改草稿,不进 `DATA_BUSINESS` 正式页;验收后才从当前代码推导出页面更新,再回头与草稿核对。这道核对关卡的性质见 [`step6-assemble.md`](./step6-assemble.md)"与草稿核对"节,那里有本流程对"强制锚定"的完整定义,本文不复述、以那一节为准。

开发产物本身的质量管理(草稿写得好不好、代码实现对不对)不归本流程管,那是 dev-pipeline 的事;本流程与 dev-pipeline 的对接方式尚未定义,当前只要求步 1 的草稿在步 6 能被取到并注明路径。

## 拆分标准

沿用初始化的拆分标准:**产物能独立检验的才单列一步;每步派独立执行者,上下文不混**。步 3(提取)与步 4(归纳)坚持分开,不合并成一步——提取者若知道归纳目标就会越权预判"这算不算一条正式分支行",与归纳者的实际归类打架。更新的提取范围虽小,同一风险不减。

更新(每次改动做一次)共六步,按顺序执行:

1. [`step1-draft.md`](./step1-draft.md) · 规则草稿(判断,**开发动手前**做,不是验收后)
2. [`step2-scope.md`](./step2-scope.md) · 定范围与分流(判断,单独做,人审后才进下一步)
3. [`step3-extract.md`](./step3-extract.md) · 提取(机械,范围限步 2 受影响节点)
4. [`step4-classify.md`](./step4-classify.md) · 归纳与 diff(判断,参照步 2 + 步 3 + 现有页)
5. [`step5-verify.md`](./step5-verify.md) · 校验(机械,换人做)
6. [`step6-assemble.md`](./step6-assemble.md) · 组装 + 与草稿核对 + 打回判定(机械)

步 1 在开发之前,步 2–6 在验收之后,中间隔着整个开发周期,这是本流程与初始化最大的形态差异。

每步三项:**范围 / 产出 / 注意**(另附通过判据与引用的规则条款)。执行到一步结束即停,报"确定项"与"不确定项";确定项直接合并,不确定项等人定。

## 批次产物路径

步 3–步 5 的中间产物落 `DATA_BUSINESS_RAW` 下 `update-<change-id>/`,与初始化批次目录(如 `DATA_BUSINESS_RAW` 下 `init-<业务>/`)同款。

## 做成 skill 前要积累的

每次执行记下三件事:分流判据(步 6)算出来的结论与人工直觉是否一致、草稿核对出现了几条不一致以及最后改的是哪一边、废弃编号处理有没有踩到反向核对豁免以外的坑。跑 2–3 次后再定阈值是否调整、能否做成 skill。
