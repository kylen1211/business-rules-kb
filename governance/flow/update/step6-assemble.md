# 步 6 · 组装、与草稿核对、收口

机械类。总则见 [`README.md`](./README.md)。

本步做四件事:把步 4 的 raw 组装进页面、把组装结果与步 1 的草稿核对、按核对结果做打回判定、收口前再复核一次分流判据。

## 范围

### 一、组装

只吃步 4 的 raw,不回头看代码、不做判断;槽位缺来源即停。按 `GOVERNANCE_RULES` 的 `assembly-rules.md` 三的模板槽位,把变更表逐行落进 `DATA_BUSINESS` 下 `<业务id>.md`:

- 状态"废弃"的行从正文移除,进页尾归档记录表(`编号 | 废弃 | change-id | commit`,硬规则 2)。
- 状态"新增"的行按编号插入对应节点表;新增节点整张表按 `Dxx` 号顺序插入决策表节。
- 状态"不变"的行原样保留,不动。
- 状态"覆盖"的无编号内容(流程文字步骤行、节点触发点 / 备注 / 恒定收尾)覆盖重写。

关联项同步只有六样,多出来的即不确定、停下交人定:

1. 引用了受影响节点的流程文字步骤行;
2. 页尾代码对照节里对应的行(含仅行号漂移的那些);
3. 页头验证基线 commit;
4. 页尾归档记录表;
5. `DATA_LOG` 追一行(`rule-update` 格式见 `GOVERNANCE_RULES` 的 `assembly-rules.md` 5.2、5.3,同时把 frontmatter 的 `updated` 刷成当次日期);
6. `ENTRY_OVERVIEW` 核心流程节对应 `kind:rule` 行——执行 [`../overview-sync.md`](../overview-sync.md),本步只负责触发,不重复其判据(该业务页此前已建成,通常落在"`page`/`tier` 字段已同步 → 无需改动"这一支)。

本流程不出现任何图相关的判断或动作——图槽位链接行、图内容是否需要重画,一律不在本步处理;若本次改动影响到某张已有图的内容,由触发者在本次更新之外、独立调用 [`../diagram-draw.md`](../diagram-draw.md) 处理,与本流程解耦,不作为本步"关联项同步"的一部分。

页面"组装自查"节的数字同步更新为组装后的值,并与"改动前的数字 ± 本批变更表的增减条数"对账。

全部改动(页面文件 + log 追加行 + 概览同步行)在同一次 `git add <挂载根>` + `git commit` 里落地,不用 `kb.sh`(见 `GOVERNANCE_RULES` 的 `overview-rules.md` 八)。**提交动作在核对通过、打回判定为"通过"之后才执行**,顺序不可换。

### 二、与草稿核对

组装出来的页面内容,与步 1 的规则草稿逐条比对。

**核对的性质(本流程对"规则先行、强制锚定"的完整定义,以本段为准):锚定的是核对这道流程关卡不可跳过(每次更新必须走草稿-代码核对),不是要求代码结果必须逐字服从草稿字面;核对发现不一致时,是改代码去符合草稿、还是改草稿去符合代码(或两者都改),由人工介入时现场判断,流程本身不预设立场。**

这一条与"规则页事实以代码为准"(`GOVERNANCE_RULES` 的 `business-rule.md` 一)并不冲突:页面内容始终从当前代码推导而来(步 3 到步 5 全程不看草稿),草稿的作用是提供一个"当初打算做什么"的比对基准,让代码跑偏时有人能发现,而不是给页面提供内容来源。

- **谁做**:人工核对逻辑一致性,不设自动 diff 算法。组装执行者负责把两边逐条摆出来、给出每条的一致 / 不一致结论并标明依据;**执行者不裁定不一致该改哪边**,凡判"不一致"一律停下交人。
- **核对范围**:步 1 草稿的全部条目 ↔ 本次组装涉及的页面内容(状态为新增 / 废弃 / 覆盖的部分)。双向都要核:草稿有而页面找不到对应内容,算不一致;页面本次新增或废弃了草稿里只字未提的规则,同样算不一致。页面上状态为"不变"的行不参与核对——草稿本就只写这次改动。
- **一致的口径**:同一组输入,在草稿与在页面上命中的结果终态相同,即为逻辑一致;措辞、行文、编号、分层组织方式可以不同,不要求字面相同。这把尺与步 4 判"规则语义变了"用的是同一把,两处口径必须一致。
- **废弃行的依据三档(封闭,不许第四种)**:状态为"废弃"的行没有正文可以和草稿逐句对(它的内容已从页面移除),草稿本身也不写"废弃"二字,所以它单独走这一套。核对表里**每一条废弃行必须填一格"废弃依据"**,取值只有三种:
  1. **配对替代** —— 该行在步 4 变更表里带着配对新增编号(步 4 判"语义变了"拆出的新旧两号,见 [`step4-classify.md`](./step4-classify.md) 一"配对登记")。依据填那个配对编号即可,本行不再单独找草稿出处,由配对的那条新增行照常与草稿对条;那条新增行若对不上,一样判不一致,不会因此漏网。步 4 没登记配对的行不许在本步自行认亲——本步是机械步,不重新判断两行是不是同一条规则的新旧号。
  2. **草稿明写** —— 填草稿的临时序号 + 被引用的原句摘录(例:`草-3:"原来命中黑名单直接挂断,本次改为转人工"`)。可引用的原句一般来自草稿产出第 4 项"替代声明"(见 [`step1-draft.md`](./step1-draft.md));草稿表格里某条规则行的文字能直接读出"这个输入以后不再走原来那个结果"的,同样可以引用。
  3. **写不出** —— 前两格都填不出来,该行直接判"不一致",按打回处理。
- **不许凭记忆核对**:"草稿隐含提及""起草时想表达的就是这个""按上下文应当是替代了原规则"这类指不到具体编号或具体文字的理由,一律不算依据,按上面第 3 档处理。这条是硬要求:本步的核对人未必是草稿起草人,凡是只有起草人才复现得出的判断,换个人核对结论就会翻转,这道关卡也就不再可靠;而配对编号写在步 4 变更表上、草稿原句写在草稿文件里,任何人都查得到、都能算出同一结论。

### 三、打回判定

**一次更新批次里只要有一条规则核对不合格,整批打回,不做部分入库。** 打回时页面文件、`DATA_LOG`、`ENTRY_OVERVIEW` 一律不落盘、不提交,该业务页维持改动前状态(与 `GOVERNANCE_FLOW` 的 `overview-sync.md`"组装未通过校验 → 不执行本动作"、`GOVERNANCE_RULES` 的 `assembly-rules.md` 五"停手待人定时当次不追加 log"一致)。

打回之后由人工介入现场判断改哪边,改完按下列回归点重跑,不另设分责流程:

- 改了代码(不论是否同时改了草稿)→ 回步 2 重跑,因为受影响范围可能已经变了。
- 只改草稿、代码一字未动 → 回本步重新核对即可,步 2–5 的产物仍然有效。

### 四、分流复核

组装完成后,用下方"分流判据"再算一次。步 2 算的是预估范围,组装完拿到的是实际结果,两者可能不同(典型情形:diff 看着只碰一个节点,归纳后发现连带废弃了半页编号)。复核结论为"废弃新建"时,本次组装作废、不提交,按 [`../README.md`](../README.md)"停止交回格式"整理依据,交回入口分诊重新判断,本流程不自行指定下一步去向。

## 分流判据:局部改 vs 废弃新建

本节是该判据的唯一定义处,步 2 的前置判定与本步的收口复核用的是同一套,两处不得各自解释。

三条线**按顺序**算,任一条命中即判"废弃新建"、命中即停不再往下算;三条全未命中才判"局部改"。

**线 1 · 业务边界变更(结构线)**
本次改动是否使该页页头"管什么 / 不管什么"任一条目需要新增、删除,或改变所指的语义?需要 → 命中。
理由:页头边界是整页归纳的前提,归类全靠它(初始化步 1 的产出是步 3 归类的共同参照)。前提变了,页上既有的归类结论就整体失去依据,局部改只会留下一批按旧边界归好的存量行,越攒越乱。
**"改变所指的语义"用的不是步 4 那把尺,别把那三项套过来。** 步 4 判"规则语义变了"量的是单条分支行(条件的判断依据 / 取值范围、结果的终态 / 输出),对象是一条条件 → 结果规则;页头条目是范围声明,没有"结果终态"可量,硬套只会让执行者在找不到对应项时自由发挥。本线的判据是**这条条目圈进来的东西有没有增减**:对每条页头条目,列出改动前它覆盖了哪些节点 / 模块,再看改动后有没有节点 / 模块进出这个集合——有进出 = 语义改变;集合一个不差、只是换了说法来描述 = 措辞润色,不算。两把尺共享同一个原则(看所指的事实变没变,不看文字变没变),但判据项各管各的对象,不通用。上文"二、与草稿核对"说草稿核对与步 4 是同一把尺,那句只管草稿核对,不覆盖本线。
机械化做法:逐条比对改动前页头条目清单,列出需增 / 需删 / 需改语义的条目(改语义的按上一段的集合增减法判),条数 ≥ 1 即命中。分不清是"措辞润色"还是"语义改变"时,一律判语义改变(取严),并记入不确定项。

**线 2 · 链路增删(结构线)**
本次改动是否新增或删除了整条链路(不是链路内的步骤变动)?是 → 命中。
理由:链路是流程文字节的组织单位,增删链路要重排整节;而且新链路进来后,"一个节点只属一条链路"这条约束要在全页范围重新检查一遍,那已经是整页级的工作量,不如直接重来。

这条理由成立的前提是链路增删通常是代码大改的伴生结果,反正要核对到接近整页级,不如直接从代码重新抽取更省事更保险。

**零 diff 例外**:若步 2 五条口径核实后,受影响节点集合里没有任何节点命中口径 1/2/3/5(没有分支行为变化、没有分支/节点增删、没有前提内容变化),链路数变化纯粹是把已核实、内容不变的既有节点重新分组呈现——线 2 不命中,不触发"废弃新建",本流程原地处理。理由:线 2 的省事账建立在"反正要整页核实"这个前提上,前提不成立时(代码零 diff、事实早已核实过)重来是纯浪费。

**线 3 · 影响面过半(数量线)**
受影响节点数 ≥ 2,**且** 受影响节点数 ÷ 改动前该页节点总数 > 1/2?是 → 命中。
- 分子 = 步 2 受影响节点集合的元素个数,含新增节点、废弃节点,以及因共享前提变更被牵连进来的节点。
- 分母 = 改动前该页决策表节的小节数(一节点一张表,硬规则 5,数表数即可),不含共享前提节的 `Mxx` 条目。
- **单节点下限**:受影响节点数 ≤ 1 时本线一律不命中,不看比例。没有这条下限,只有一两个节点的小页改动一个节点就要整页重做,代价明显不成比例。
- 页面节点总数本身少于 2 的极小页,本线永远不命中,只靠两条结构线判。

判定示例(两个极端):某节点一个分支的超时阈值从写死改成可配置——页头边界不变、链路不增删、受影响节点数 1 触发下限,三线全未命中,判局部改;业务范围从"只管快脑工具受理"扩到"含慢脑回流"——页头"管什么"要加条目,线 1 命中即停,判废弃新建,不必再数节点。

## 产出

- 更新后的业务页 `DATA_BUSINESS` 下 `<业务id>.md`(含组装自查节新数字、归档记录新行);
- `DATA_LOG` 一条 `rule-update` 记录;
- `ENTRY_OVERVIEW` 核心流程节对应 `kind:rule` 行的同步结果(可能是"确认无需改动");
- 草稿核对结论表:逐条一致 / 不一致 + 依据;本批每一条废弃行在表里各占一行,另填"废弃依据"一格(配对编号 / 草稿序号加原句 / 写不出),写不出即该行判不一致;
- 分流复核结论(三线逐线依据 + 结论);
- 以上页面类改动同一次 git 提交。

打回时的产出只有草稿核对结论表与打回说明,页面类产物一律不生成。

## 注意

- **核对不通过时不要"先提交页面、再补改"**:打回即整批不入库,页面维持原状;部分入库会让页面处于"一半按新代码、一半按旧代码"的状态,后续任何一次更新的 diff 基准都不可信。
- 页面改动、log 追加行、概览同步行三者是同一次提交,不拆开;提交前三者都要落盘完毕。
- 归档记录表的 `change-id | commit` 两列要与 log 条目的对应字段一致,交叉核对靠这两个字段对齐,不靠复述编号明细(`GOVERNANCE_RULES` 的 `assembly-rules.md` 5.5)。
- 本步是本流程唯一动 `DATA_BUSINESS` 的地方;步 1 到步 5 全程不碰正式页。
- 现有页若还带着早于可读性规范(`GOVERNANCE_RULES` 的 `business-rule.md` 六)与页头跨链接规范(同文件八)的旧写法,本次更新触碰到的那些行顺带按新规范改写,未触碰的行不回改、不单独起一轮改造。

## 通过判据

按顺序全过才算通过,任一项不过即打回:

1. 模板六节槽位无缺失(缺来源即停);变更表每一行都在页面上找到对应落点,状态"废弃"的行确已移出正文并出现在归档记录表。
2. 页面"组装自查"节四项数字与"改动前数字 ± 本批变更表增减条数"逐项对上。
3. 草稿核对结论表覆盖步 1 草稿全部条目**与本批全部废弃行**,每条废弃行的"废弃依据"格已填且落在三档中的前两档,且**不一致条目数为 0**;出现 ≥ 1 条即整批打回。
4. 分流复核三线全未命中(命中即本次组装作废,按上方"四、分流复核"停止交回入口分诊)。
5. 页面文件 + log 追加行 + 概览同步行在同一次 git 提交里。

## 引用的规则条款

- 模板槽位(`GOVERNANCE_RULES` 的 `assembly-rules.md` 三)
- 硬规则 1(编号终身不复用)、2(页面只显示在用;归档记录)、5(一节点一张表)(`GOVERNANCE_RULES` 的 `assembly-rules.md` 二)
- log 记录规则,含 `rule-update` 行格式与追加时机(`GOVERNANCE_RULES` 的 `assembly-rules.md` 五、5.2、5.3、5.4、5.5)

- 规则页事实以代码为准(`GOVERNANCE_RULES` 的 `business-rule.md` 一);可读性与页头跨链接规范(同文件六、八)
