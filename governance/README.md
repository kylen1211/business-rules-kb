## 一、这是什么

一句话:**把项目的业务逻辑整理成"条件→结果"的规则清单,作为需求、开发、测试共同对齐的统一标准源。** 代码必须对上清单——那是验收手段,不是目的。

想知道"这块业务现在的规则是什么、系统该有什么行为",看这里就行——不用翻代码,不用靠猜,不用问"当时是谁改的"。

## 二、为什么需要它

**AI 写代码快,最容易出的问题是**:没人说得清现在的规则到底是什么。

- 文档和代码脱节,时间一长文档没人信;
- 新人(或新开的 AI 会话)接手,只能翻代码、靠猜;
- 改一处逻辑,不知道会不会踩到没人记得的隐藏规则。

**统一标准源换来两样东西**:

- **长期项目资产**:提需求、写代码、设计用例,对齐的都是同一份清单,而不是各自的理解;PRD、架构设计、测试用例都能以它为底座生成——尤其"条件→结果"几乎能逐条翻译成测试用例;
- **人和 AI 的共同语言**:"条件→结果"人读着清晰,AI 也能准确执行,避免"说的和做的不是一回事"。

**取舍**:比"想到什么就直接改"重——多花时间定规则、留记录、走核对,换的就是上面这份资产;项目越久,越值钱。

## 三、核心原理:统一标准源,规则先行

**底线只有一条**:任何业务逻辑都必须落在规则清单上。清单是裁决对错的尺子——**要改行为先改清单,代码向清单对齐**;一处对不上,这批改动就不算完成。

**落地只有两种场景**:

- **旧代码补记录(初始化)**:从现有代码反推规则,逐分支列成清单。这是唯一"代码在前"的例外:反推只是建基线的翻译手段;基线建成后标准就是清单,找问题、定决策都从清单入手。
- **新功能(更新)**:先写规则草稿,照草稿开发;开发完拿最终代码反推一遍,和草稿逐条核对,全对上才定稿。

**三条纪律**:

- **核对靠代码本身,不靠工具。** 自动化没接上,人照样拿代码核对,规矩不松动。
- **不一致时人来裁决。** 改代码还是改规则当场判断,不预设谁对谁错(清单也可能起草错);裁决落定的清单,就是新标准。
- **规范唯一,违例不合入。** 页面、流程、图各有唯一规范(学 Linux 社区的文档治理);守住规范,体系才能长期不崩。画图规范随项目自带:`.claude/skills/sum-svg-diagram/`(两张骨架母版+几何自检脚本),换环境也不丢标准。

## 四、在开发流程中的位置

```
需求判断 → 技术设计 → 开发实现 → 测试验收 → 代码审查 → 部署上线
              ↑规则草稿              ↑规则核对定稿
```

图上两处标注就是清单进流水线的位置,对应"新功能(更新)"场景;初始化建库是一次性动作,不走这条流水线。流水线中间产物(PRD、设计稿)是一次性变更文档,交付即归档;**长期判据以规则清单为准**。

**任何改动:先判断该不该做,再改清单,再动代码;代码最终必须对上清单。**
